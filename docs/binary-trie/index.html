The Partitioned Binary Tree — variable-key variant

What is being built on this branch, how the tree and its state embedding work, and why the design looks the way it does. The implementation is a generic compressed binary radix trie carrying EIP-8297’s state embedding with the variable-length key scheme of EIP-7864’s partitioned rewrite.

EIP-8297 (draft) EIP-7864 (draft) src/ethereum/binary_trie/ hash: BLAKE3 (not final)

What this is

Ethereum wants blocks provable with validity proofs, and the Merkle Patricia Trie is the obstacle: hexary branching, RLP node encoding, Keccak, a tree-of-tries indirection, and monolithic code blobs make its witnesses enormous. The EIP’s worst-case arithmetic: a 60M-gas block touching one byte each of many distinct unchunked contracts needs to reveal ≈ 1.8 GB of proof data.

EIP-8297 replaces all of it with a single binary tree — accounts, storage, and contract code in one structure — partitioned into zones by state category. This branch implements a variant that goes further than either published draft: the variable-length key scheme EIP-7864 adopted in its partitioned rewrite (PR 11832) — a full zone byte and untruncated digests instead of 4 zone bits squeezed into a fixed 32-byte key — on a tree rebuilt as a generic compressed radix trie: prefix-carrying branch nodes and full-key leaf nodes with domain-tagged hashing — no stem node type, and no separate extension node. Two modules:

ModuleResponsibility
binary_trie/trie.pyThe raw tree: variable-length prefix-free keys → 32-byte values, node types, merkleization, root computation. Knows nothing about Ethereum state.
binary_trie/embedding.pyThe mapping of accounts, storage slots, and code chunks onto tree keys and 32-byte values: zones, key derivation, code chunkification.

Tests mirror the split (tests/test_binary_trie.py, tests/test_binary_trie_embedding.py), with the EIP’s insertion-based reference implementation ported (adapted to variable keys) as an in-test oracle — the spec code and the reference must produce identical roots.

Running the code

The implementation is pure Python — nothing to compile. The only build-ish steps are dependency resolution (uv manages the environment, including the blake3 native wheel) and static checking. From a fresh clone:

git clone https://github.com/ethereum/execution-specs
cd execution-specs
git switch projects/binary-trie
uv sync                       # creates .venv and installs all dependencies

Run the binary trie test suites (spec code cross-checked against the ported EIP reference implementation):

uv run pytest tests/test_binary_trie.py tests/test_binary_trie_embedding.py -v

Type-check the package (the repo runs strict mypy):

uv run mypy src/ethereum/binary_trie

Try it interactively — insert two keys sharing a stem and compute a root (a 33-byte stem plus sub-index byte, the account/code key shape):

$ uv run python
>>> from ethereum_types.bytes import Bytes, Bytes32
>>> from ethereum.binary_trie.trie import BinaryTrie, trie_set, root
>>> trie = BinaryTrie()
>>> stem = b"\x00" + b"\x42" * 32
>>> trie_set(trie, Bytes(stem + b"\x00"), Bytes32(b"\x01" * 32))
>>> trie_set(trie, Bytes(stem + b"\xff"), Bytes32(b"\x02" * 32))
>>> root(trie).hex()

Or derive state keys through the embedding:

>>> from ethereum_types.bytes import Bytes20
>>> from ethereum.binary_trie.embedding import (
...     address20_to_address32, get_tree_key_for_basic_data)
>>> addr = address20_to_address32(Bytes20(b"\xaa" * 20))
>>> get_tree_key_for_basic_data(addr).hex()  # 34 bytes; first byte 00 = account zone

The full static suite CI runs is just static (requires just ≥ 1.40; the individual commands are ruff check, ruff format --check, mypy, codespell, vulture, and ethereum-spec-lint, all via uv run).

The tree: a compressed binary radix trie

The entire public contract is a flat map: trie_set(trie, key, value) and trie_get(trie, key) where the value is exactly 32 bytes and the key is variable-length bytes, plus root(trie) reducing the whole map to one hash. No RLP, and no node type with Ethereum semantics.

Two node types make up the tree: a branch splits on one bit and carries the run of bits every key below it shares (there is no separate extension node — the prefix lives on the branch, after eth-act’s zkvm-ethereum-mpt representation), and a leaf holds one key’s value, committing its full key so its meaning never depends on the path taken to reach it. The structure is canonical by construction, not by rule: a branch must have two non-empty subtrees, which forces its prefix to be exactly the shared run — a shorter prefix would leave every key agreeing on the split bit, emptying one side. A non-canonical tree is unrepresentable, so one committed state has exactly one node structure and one root, and proof verifiers have no well-formedness side-conditions to enforce.

One requirement replaces the old fixed-size check: keys must be prefix-free — a leaf ends a path, so a longer key could never pass through the position a shorter one terminates at. The embedding guarantees it by giving every key of a zone one fixed length; the tree asserts it while splitting keys, where a violation surfaces as a key running out of bits before separating from its group.

Merkleization rules — domain-separated

  • Leaf → H(0x00 ‖ full_key ‖ value)
  • Branch → H(0x01 ‖ bit_count2B ‖ packed_prefix_bits ‖ left ‖ right)
  • Empty trie → 32 zero bytes (a sentinel, not a hash output).

The tag byte and the explicit bit count are load-bearing, not cosmetic. The tags keep the two preimage kinds apart even where their lengths coincide, so a leaf can never be re-presented as a branch or vice versa; the count keeps prefixes injective, since without it a prefix of 0110 and one of 01100 would pack to the same padded byte and two different trees would share a root. Fusing the prefix into the branch also means one hash per compressed run instead of the two an extension-plus-branch pair would cost. And a side effect of canonical form: branches always have two real children, so empty siblings do not exist — the old zero-collapse rule is gone, and every sibling in a witness is a real hash.

The maximum key length, derived from the count field

Any finite length field creates a bound somewhere; the design choice is only where to surface it. Here is the chain:

  1. The encoding fact. The bit count is two bytes, so the largest representable prefix is 2¹⁶ − 1 = 65 535 bits. A longer prefix has no encoding at all.
  2. The worst case a prefix can be forced to. A prefix is a run shared by at least two keys, ending at their first differing bit — the split bit, which is not part of the prefix. Two distinct L-byte keys can agree on everything except their final bit, forcing a prefix of 8L − 1 bits. (Keys of different lengths must diverge within the shorter one — anything else is a prefix violation — so the shorter length governs.)
  3. Solve. 8L − 1 ≤ 65 535 gives L ≤ 8 192 bytes, and the bound is exactly tight: two 8 192-byte keys differing only in their last bit need a prefix of precisely 65 535 bits.

Hence MAX_KEY_LENGTH = 8192, enforced unconditionally in trie_set. The placement is the point: a too-long key is harmless alone (it becomes a leaf, whose preimage has no count field) and only breaks the encoding when a second long key shares enough bits with it — a content-dependent failure deep inside merkleization, dependent on what the key’s neighbours happen to be. Checking at insertion converts that into an unconditional contract at the boundary; the assert inside encode_bit_prefix remains only as a backstop restating this derivation. The embedding’s longest key is 66 bytes, so the ceiling carries ~124× headroom — it exists to make the encoding’s implicit assumption explicit, not because anything approaches it.

Zones: the partition lives inside the key

The zone is not metadata stored next to a key — it is the first byte of the key. Because the trie consumes key bits MSB-first, forcing a category’s keys to share their first byte gives every zone its own exact region of the key space, and with it its own region of the tree. (Under radix compression the zone boundary need not coincide with a physical node — a branch’s prefix may swallow the zone bits along with whatever follows them — but the region of keys under the prefix stays exact, which is what sync and expiry schemes actually operate on.)

Keys are variable length, and that is what makes the full-byte label affordable: the zone byte is prepended to the key rather than carved out of a fixed stem, so digests keep their entire 256-bit width and a zone’s one-byte-wide prefix says nothing about its capacity — every zone’s key space is unbounded behind its label. Prefix-freeness comes free of charge: keys of the same zone all have the same length, and keys of different zones differ in byte 0.

The lengths are not left implicit. The embedding declares them as documented constants — ACCOUNT_KEY_LENGTH and CODE_KEY_LENGTH (34) and STORAGE_KEY_LENGTH (66) — and every derivation function asserts the length of the key it constructs against its zone’s constant. The two halves of the prefix-freeness argument each enforce their own side: the embedding proves it only emits fixed-length keys per zone, and the tree asserts no key prefixes another while splitting keys in root(). A future change to the digest width fails loudly at the first key derivation instead of silently reshaping the tree.

ZoneByteHoldsKey length
account 00x00Account headers: basic data, code hash, first 64 slots, first 128 code chunksACCOUNT_KEY_LENGTH = 34
code 10x01Overflow code, content-addressed by code hashCODE_KEY_LENGTH = 34
2 – 2540x02–0xFEReserved for future state categories—
storage 2550xFFOverflow storage (slot 64 and up), bucketed per accountSTORAGE_KEY_LENGTH = 66

Storage sits at the far end of the byte, but its slice of the top-level key space is the same 1/256 as everyone else’s — under variable keys, capacity lives behind the prefix, not in its width. Contrast with published EIP-8297, where partitioning inside a fixed 32-byte key forced storage to claim half the tree with a 1-bit label just to keep enough hash bits.

The embedding: state → keys and 32-byte values

The tree is deliberately ignorant of Ethereum. The embedding is the rulebook that injects accounts, storage, and code into the flat key space — a set of pure key-derivation functions plus two value encoders. Same tree, different embedding, would be a different protocol. Since the radix refactor even the stem is pure embedding vocabulary, defined here and nowhere else: a key’s stem is every byte except its final sub-index byte. Keys sharing a stem form one group of up to 256 co-located values; the tree has no stem node type (and no Stem type in code — the word names a concept, not a structure), the stem surviving only as a shared bit prefix carried by the branch below it, so a group’s values still open together in one branch. One named constant keeps the old vocabulary for EIP-table fidelity: STEM_SUBTREE_WIDTH is now simply the maximum group size — the sub-index byte’s space — with no fixed subtree behind it; a group commits through only its occupied leaves.

The account header stem

One stem per account, in the account zone, derived from the address alone: get_tree_key(ACCOUNT_ZONE, key_hash(address), sub_index). Its 256 sub-indices are budgeted so the data touched together in typical transactions sits under one branch opening:

Sub-indexContents
0basic_data — version, code size, nonce, balance packed big-endian into one leaf
1code_hash — hash of the contiguous bytecode (see below)
2 – 63reserved
64 – 127storage slots 0 – 63
128 – 255code chunks 0 – 127 (first ~4 KiB of code)

Overflow storage

Slot 64 and beyond move to the storage zone. The stem recipe is 0xFF ‖ H(address) ‖ H(address ‖ tree_index): two full digests. The first gathers all of an account’s overflow storage under one contiguous subtree — the unit future expiry and partial-statelessness schemes prune or sync — with the full 256-bit prefix ruling out bucket collisions outright, not just probabilistically. The second spreads the account’s 256-slot groups within that bucket; binding it to the address too means storage keys ground to sit close together in one contract can’t be reused to attack another (the DoS rationale stated in the 7864 rewrite).

Value encodings

Everything is squeezed into exactly 32 bytes. encode_basic_data packs four scalars into fixed big-endian fields (4 reserved ‖ 4 code-size ‖ 8 nonce ‖ 16 balance). chunkify_code slices bytecode into 31-byte pieces, each prefixed by one byte counting how many of its leading bytes are push-data spilling in from the previous chunk — so any single chunk plus its Merkle branch can be interpreted (jump destinations included) without fetching its neighbors. That property is what makes per-chunk code proofs sound.

Where code lives — and why there is no code root

Code is split across two homes. Chunks 0–127 sit in the account header stem (sub-indices 128–255). Chunks 128+ go to the code zone in groups of 256, keyed by get_tree_key(CODE_ZONE, key_hash(code_hash ‖ tree_index), sub_index) — addressed by what the code is, not who deployed it, so identical bytecode deployed a thousand times occupies one set of leaves. Most deployed contracts are copies of a few templates; this deduplicates all of them past the first ~4 KiB.

There is deliberately no per-contract code commitment. In the MPT, code lived outside the trie and code_hash was its only commitment. Here the inversion is total: the chunk leaves are the committed representation, covered by the single tree root like any storage slot. The code_hash leaf survives as plain data for two jobs: EXTCODEHASH must keep answering with the hash of contiguous bytecode, and the overflow-chunk keys are derived from it. Its consistency with the chunks is an invariant the state transition maintains, not something the tree structure enforces.

Proving code chunks: derivation, not selection

Two questions come up immediately when code has no commitment of its own, and both have answers that are easy to get wrong on first read.

“To prove against code_hash, don’t I need all of the code?”

No — because code_hash plays two different roles in a chunk proof, and neither uses it as a hash:

  • As a proven value: one Merkle branch shows the state root commits to the 32-byte value X at the account’s code-hash leaf. Its keccak preimage is never touched — the branch proves “this account’s code identity is X,” treating X as an opaque identifier.
  • As key material: knowing X, the verifier computes the chunk’s key — get_tree_key(CODE_ZONE, key_hash(X ‖ tree_index), sub_index), pure arithmetic on 32 bytes — and checks a second branch there.

The chunk’s integrity flows from the state root, not from recomputing keccak(code): the tree committed to every chunk individually at deploy time. The caveat worth knowing: the proof establishes “the tree stores this value where chunk i of code-with-identity-X lives” — it does not re-verify that the chunks reassemble to a bytecode whose keccak is X. That correspondence is an invariant the state transition welded in at deploy, when chunks and hash were written from one blob. The full bytecode is therefore needed only where that invariant is established, never where it is used: once per deploy inside a validity proof (hash + chunkify the returned code), once per account in the EIP-7748 migration, and by any verifier whose only trust anchor is code_hash itself rather than a state root — which is precisely the verifier this design tells you not to be.

“How do I know the chunk I picked belongs to this account?”

You never pick — the verifier derives every key itself, starting from the address, so nothing else can be presented. Belonging is enforced by key computation, not inspection:

  • Chunks 0–127 (header): direct — the key is get_tree_key(ACCOUNT_ZONE, key_hash(address), CODE_OFFSET + i). The address is in the derivation; another account’s chunk sits under a different stem by construction.
  • Chunks 128+ (content-addressed): a two-link chain whose anchor still lives in the header, even though the chunk does not — the header’s role shifts from containing the chunk to supplying the link. From the address, derive the code-hash leaf’s key (account zone) and verify that branch, yielding X; from the proven X and the chunk number (which fixes tree_index and sub_index arithmetically), derive the chunk key (code zone) and verify the second branch. Both branches must verify against the same root at keys the verifier computed — substituting foreign code requires either a wrong X (blocked by link one) or a hash collision. The code zone itself contains no account information at all: nothing in it can prove ownership, and that is the mechanism of dedup — many accounts’ code-hash leaves bridge to the same code-zone region. In practice the header branch is nearly free, since a transaction touching the account opens the header stem for basic data anyway and the code-hash leaf shares that branch.
address ──derive──▶ key of code-hash leaf ──prove──▶ X
X, i    ──derive──▶ key of chunk leaf     ──prove──▶ chunk

Two refinements complete the picture. First, “belongs to this account” is deliberately non-exclusive for overflow chunks: identical bytecode deployed twice shares physical leaves, so the same chunk legitimately belongs to every account whose code-hash leaf reaches it — that is the dedup working, while header chunks stay exclusively per-account. Second, full EVM semantics usually want a third leaf: code_size from the basic-data leaf, to know whether chunk i is within the code at all (reads past the end return zeros). It lives in the same header stem as the code-hash leaf, sharing nearly the whole branch already being opened — the header co-location earning its keep again.

The shape to remember: the value proven by one branch feeds the key derivation of the next. This dependent-proof structure is something the future witness format must be able to express, and it is unique to the content-addressed part of the design.

Design decisions and why

Binary branching (arity 2)

Witness size is 32·(k−1)·log N / log k — minimized at k = 2. For 224 elements: 768 bytes per branch binary, versus 1 152 (k = 4), 1 792 (k = 8), 2 880 (k = 16), and the MPT’s ~5 760. Halving the branching factor is the single biggest witness win available.

One tree instead of a tree of tries

Database access, caching, sync, proof creation, and gas rules all operate on one key/value abstraction. And with no storage_root stored in any leaf, writing an account’s nonce and one of its slots are independent writes whose branches only meet near the root — root recomputation parallelizes across zones, across accounts, and across stems.

Variable-length, prefix-free keys

Adopted from EIP-7864’s partitioned rewrite, replacing published 8297’s fixed 32-byte keys. The zone byte is prepended instead of displacing digest bits, so nothing is truncated, no collision-margin analysis is needed, and the bit-packing machinery vanishes from the embedding. The price: prefix-freeness becomes an invariant rather than a length check — so the embedding declares per-zone key lengths as constants and asserts them at every derivation, while the tree asserts no key prefixes another when splitting. Preimage framing, the other cost, is handled by the radix design’s tagged hashing.

A generic radix trie — no stem nodes, no extension nodes

Stem nodes and their fixed 256-leaf subtrees are replaced by just two node types — prefix-carrying branches and full-key leaves, following eth-act’s zkvm-ethereum-mpt representation, but fused into the commitment itself rather than only the in-memory form. Branch prefixes compress the manufactured runs inside H(address) storage buckets (~250 empty-sibling levels → one node) and cap adversarial prefix grinding at O(1) added proof depth instead of O(shared bits); sparse stems commit through only their occupied structure. The decisive property of the fusion: canonical form is unrepresentable to violate — two-non-empty-children forces every prefix to be exactly the shared run, so the verifier obligation to reject non-canonical structure disappears with the extension node itself. Domain-tagged hashing remains mandatory (variable-length preimages can no longer be framed by accident). The honest cost: fixed 256-leaf subtrees were maximally SNARK-friendly; variable structure reintroduces data-dependent branching in circuits, and splitting a run now rewrites the surviving branch’s hash, which client node-dedup storage will notice.

Zones for structure without a side registry

Every zone owns an exact key-space region behind its byte, and an account’s storage bucket owns the region behind its H(address) prefix — the units that state expiry, partial statelessness, and separate sync operate on, with no auxiliary structure needed. The chain problem this used to carry (stems inside a bucket sharing up to 256 manufactured prefix bits, producing long empty-sibling runs) is closed by the radix refactor: one branch prefix carries the entire shared run.

Content-addressed overflow code

Keying big code by code_hash removes mass duplication from state. The first 128 chunks stay per-account so an account’s core data, hot storage, and initial code expire together in one step with no reference counting; only the shared overflow leaves need refcounts or a sweep when expiry arrives.

Hash function left open — BLAKE3 for now

Candidates are BLAKE3 (fast native, reasonable in-circuit), Keccak (already in Ethereum, costly to prove), and Poseidon2 (excellent in-circuit, security analysis ongoing). Because the tree depends only on a hash — no elliptic curves — it stays post-quantum sound where Verkle’s curve-based stack does not; fast recursive proving is expected to recover the prover speed that was Verkle’s main advantage.

Decisions specific to this port

The execution specs are a specification — readability wins over performance, and a few choices here follow from that plus review hardening:

  • Repo-MPT-shaped API. BinaryTrie / trie_set / trie_get / copy_trie / root mirror merkle_patricia_trie.py, so a future fork integration swaps tries without changing call shapes.
  • The hash sits behind one function. Since the EIP marks the hash as not final, blake3_hash in trie.py is the only place BLAKE3 is invoked; merkleization and key derivation both delegate to it, making a future swap a one-line edit.
  • Guards are kept, not typed away. trie_set asserts a non-empty key and a 32-byte value, every embedding derivation asserts its constructed key matches its zone’s declared length constant, and the tree asserts key-level prefix-freeness while splitting — a key running out of bits while still grouped with others is a prefix violation, so each check lives exactly where its property matters.
  • Canonical form comes free from the rebuild. The dict-backed spec rebuilds the node structure from scratch on every root(), so the insert/split/merge/delete machinery clients need — and the canonicity bugs that live in delete-time merging — simply do not exist in the spec.
  • An insertion-based radix reference is the test oracle. Independently written (standard descend/split insertion, its own tagged hashing), it cross-checks every root over randomized 32-byte and mixed 34/66-byte key sets — and because it builds incrementally while the spec rebuilds, agreement on every root is also a check that both constructions produce the same canonical structure.

Where this variant sits between the two EIPs

In July 2026 EIP-7864 — the older unified binary tree that 8297 builds on — was rewritten to a partitioned design with variable-length keys (PR ethereum/EIPs#11832). This branch initially implemented published EIP-8297 verbatim (fixed 32-byte keys, 4-bit zones, stem nodes), then pivoted to the rewrite’s key scheme, and finally replaced the stem-node tree itself with a compressed radix trie — keeping 8297’s choices wherever they are orthogonal. What was taken from where:

DimensionThis branchTaken from
Key shape Variable-length, prefix-free: zone byte ‖ full digest(s) ‖ sub-index (34 B account/code, 66 B storage) 7864 rewrite
Partition label Full byte — account 0, code 1, storage 255, 2–254 reserved 7864 rewrite
Storage locality H(address) ‖ H(address ‖ tree_index) — an account’s entire overflow storage in one contiguous subtree; double hash blocks cross-contract grinding reuse 7864 rewrite
Code addressing Content-addressed by code_hash — identical bytecode shares leaves (the rewrite keys code per account; dedup is orthogonal to key shape, so it stays) 8297
Header co-location 64 storage slots + 128 code chunks in the header stem (the rewrite shrinks this to 4 + 16; a separate decision, not adopted) 8297
Tree & merkleization Compressed radix trie — prefix-carrying branches and full-key leaves, domain-tagged hashing, canonical form unrepresentable to violate. Replaces both drafts’ stem-subtree merkleization (direction from the later binary-trie discussions and eth-act’s zkvm-ethereum-mpt; EIP-3102 lineage) Neither

What the pivots gave up is published 8297’s uniformity stance: state is no longer spread evenly — an account’s storage deliberately concentrates in one subtree for syncability and expiry, the trade the 7864 rewrite made explicitly when it deleted its uniformity rationale. The two design points the variable-key pivot surfaced — preimage framing and the empty-sibling chains inside storage buckets — are both answered by the radix refactor (tagged hashing; prefix compression), but the answers themselves now belong upstream: neither published draft specifies tagged node commitments, prefix compression, or the fused-branch representation that makes canonical form unrepresentable to violate.

Caveat: both EIPs are drafts and this branch is deliberately ahead of both — no published spec matches it exactly. The hash function and gas calibration (EIP-4762’s branch costs assume shallower trees) are still in motion. This page describes the design as implemented on projects/binary-trie today.
